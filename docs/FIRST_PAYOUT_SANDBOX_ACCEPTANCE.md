# First-payout sandbox acceptance

This operator-only runner uses the same pilot approval, attempt, transfer/payout parsing, signature verification and reconciliation ledgers as the LIVE pilot. It accepts TEST credentials only and a loopback PostgreSQL `openpayables_test` database. A dedicated sandbox may lack the LIVE payer capability/KYC status; the shared reader marks this explicitly as `sandbox_not_required`, accepted only by `pilot_test` ledgers. Recipient readiness, fresh funding, identity, exact transfer and payout evidence, and one-shot constraints still apply. The LIVE execution CLI remains disabled. No hosted DB migration, LIVE key, real contributor or money is involved.

Set `OPENPAYABLES_TEST_DATABASE_URL`, `OPENPAYABLES_STRIPE_TEST_SECRET_KEY`, `OPENPAYABLES_SANDBOX_PLATFORM_ACCOUNT_ID`, `OPENPAYABLES_SANDBOX_RECIPIENT_ACCOUNT_ID`, and `OPENPAYABLES_SANDBOX_TOPUP_ID` in the local operator session. Use a dedicated TEST credential with least privileges needed for sandbox account, balance, top-up, transfer and payout reads and one simulated transfer; do not paste keys into logs or source. Use secure storage and a masked prompt. The runner fixes the amount to 500 cents and creates a synthetic project/credit, then uses the actual sandbox funding receipt to freeze a `pilot_test` approval. It refuses a different frozen recipient, receipt or amount. It does not create a top-up, account or bank payout. Do not reset the immutable pilot tables to rerun execution. Keep acceptance evidence.

1. `node --import tsx src/cli/sandbox-pilot.ts prepare` creates or displays the single frozen sandbox approval. Check `approved_not_attempted`, exact payer, recipient, receipt, and 500 cents. No Stripe POST occurs.
2. Configure the Stripe CLI for the exact dedicated sandbox; verify account identity with `stripe whoami --format json` (do not print API keys/config). Use a sandbox-authenticated CLI listener forwarding platform snapshot events to `http://127.0.0.1:8789/stripe/sandbox/platform` and connected-account snapshot events to `http://127.0.0.1:8789/stripe/sandbox/connected`. Load the CLI's signing secret securely as `OPENPAYABLES_SANDBOX_WEBHOOK_SECRET` in the listener-server session. `node --import tsx src/cli/sandbox-pilot.ts webhook` binds loopback only. Do not use the LIVE webhook secrets. The sandbox listener accepts the same Stripe CLI signing secret for both test routes, unlike the separate LIVE endpoint secrets.
3. After verifying the listener, run `node --import tsx src/cli/sandbox-pilot.ts execute APPROVAL_UUID YES_EXECUTE_ONE_TEST_TRANSFER` with the exact approved UUID. This makes at most one simulated Stripe transfer. Inspect console evidence and `status`. If an attempt exists but outcome is unknown, never rerun execution; inspect sandbox Workbench and `reconcile tr_ID` with the exact transfer ID. No fresh attempt is allowed.
4. Verify actual signed transfer events were received and routed to reconciliation, not just a locally generated signature. Wait for a standard automatic sandbox payout and use the signed connected payout event or `payout po_ID` to reconcile. The payout-only balance-transaction lookup matches the destination-payment ID; incomplete pages fail closed. Do not create a manual payout to substitute for automatic-payout attribution. The earlier $8 sandbox payout verified the API contract but does not prove this new transfer's payout. `status` reports provider observations, never independent bank receipt. Record actual acceptance results and stop the listeners when finished.

All commands are from the OpenPayables repository and use installed local dependencies. Do not deploy the sandbox listener publicly. Production deployment, actual HTTPS delivery, compliance/recipient verification, funding and authorization remain separate gates.
