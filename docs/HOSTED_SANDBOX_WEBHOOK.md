# Hosted TEST webhook reference (deployment candidate)

OpenPayables is hosting-independent. An existing application may import the server-side handler, a standalone operator may deploy the same handler independently, and a CLI-only operator may reconcile on demand. Availability of an HTTPS endpoint does not require a continuously executing Node.js process. No DigitalOcean purchase is needed for this reference. Each operator owns its Stripe account, funds, database and secrets. This is a TEST-only acceptance adapter, not a general-purpose LIVE payment API.

## Implementation

- `src/server/sandbox-webhook.ts` authenticates original bytes, enforces TEST event scope and a 1 MiB bound, dispatches to a supplied reconciliation callback, and returns 200 only after successful processing (503 for retryable processing errors). Unknown or unmatched signed events are acknowledged without creating a payment. The existing loopback TEST CLI shares the same dispatcher; existing LIVE entry points are unchanged.
- `openpayables/server` exposes `createSandboxWebhookHandler` and `createHostedSandboxWebhookHandler` in the development build. The first is a standard `Request`/`Response` adapter; its caller owns the reconciliation callback and secure runtime configuration. The second is a restricted reference for one already executed TEST pilot. Neither introduces a payment-execution route. Do not ship a browser bundle containing this server-only module or its secrets.
- Vercel's framework-independent Node.js functions in `api/stripe-sandbox-connected.ts` and `api/stripe-sandbox-platform.ts` call the same reference factory. Root `vercel.json` defines the build and static output directory; no Next.js dependency or always-running process. Node 24 is required by the existing package. The `public` directory contains only a generic landing page. Use separate TEST-only Vercel project/environment, not BlindStats or RandomPlayables. API signatures follow https://vercel.com/docs/functions/runtimes/node-js; actual deployment remains to be verified.

Select a provider supporting this database name, a dedicated custom login, and verifiable TLS using a system-trusted CA. Do not relax the existing database identity guards to accommodate a provider. Use a dedicated migration/seed administrator offline; do not place its credentials in Vercel.
2. Apply existing migrations 001–014 through the trusted operator process. Copy only the exact synthetic pilot's prerequisite rows, frozen approval, original durable attempt and transfer observation from the local acceptance ledger. Preserve historical actors/timestamps via a reviewed restricted import process that respects the triggers (do not disable safeguards or copy unrelated rows). The original local ledger remains unchanged. Prefer an initially absent hosted payout trace to demonstrate that the actual delivered event appends the paid observation; record that the new hosted ledger is a selective acceptance copy, not an independent execution. Never call `prepare`, `execute`, or create any new transfer or payout to seed it. The seed/import procedure and hosted database setup are the next implementation task, not performed by this patch.
3. Grant the login `openpayables_test_webhook` CONNECT on the dedicated database, USAGE on schema `openpayables`, SELECT on `live_pilot_approvals`, `live_pilot_attempts`, `live_pilot_transfer_observations`, `live_pilot_payout_observations`, and INSERT only on the last two observation tables. No approval/attempt writes, update/delete/truncate, DDL, admin role membership, broad grants or execution permissions on money-moving APIs. Confirm PUBLIC and inherited grants do not defeat isolation. The hosted handler checks actual role/database and dangerous grants before reconciliation. Configure a TLS-verifying PostgreSQL URL without query options; the adapter uses `ssl: { rejectUnauthorized: true }`, one connection per authenticated matching request, bounded connect/statement times and closes the pool before acknowledgement. Validate connection and resource use during hosted acceptance.
4. Create a restricted `rk_test_` key for the exact Stripe sandbox payer with only the read permissions required for account, balance, transfer, payout and balance-transaction retrieval in the proper account scope. Never use a write-capable or LIVE credential. A restricted prefix alone does not establish read-only permissions; verify them in Stripe. Register separately scoped TEST webhook destinations for `/api/stripe-sandbox-connected` and (if needed) `/api/stripe-sandbox-platform`. Use independent endpoint signing secrets, not the old Stripe CLI secret. Configure only required server-side environment variables (see `.env.example`); ensure the intended endpoint is publicly reachable by Stripe without disabling authentication on unrelated apps. Do not expose configuration, credentials or raw payloads in logs.
5. Set the exact frozen approval/payer/recipient/transfer/payout IDs from `PROJECT_HANDOFF.md`. No other pilot is accepted by the hosted reference. No automatic migration, transfer approval, execution, or payment endpoints exist in the adapter. No LIVE secrets. Before configuring Stripe destinations verify missing/invalid signature rejection and wrong method response.
